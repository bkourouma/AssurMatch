# Feature Specification: CMS minimal pour le rôle Content Admin (FAQ, guides, glossaire, surcharges légales par pays)

**Status**: Validated par défaut (lot 9 mandaté par le superviseur le 2026-10-22 ; hypothèse H7 « validée par défaut, à confirmer » ; aucun `[NEEDS CLARIFICATION]`)
**Input**: PRD (rôle Content Admin), constitution (principes II, IV, VI, VIII), specs 045 (site institutionnel bilingue), 050 (réécriture éditoriale, charte), 051 (ajout pays), 056 (consoles admin, journal d'audit), 043 (cycle brouillon → publication des formulaires de devis).
**Impacted surfaces**: Backend API (nouveau module `content-cms`, routes `/admin/content/*` et `/public-content`), base de données / Prisma / migration `0038` (table `ContentEntry`), shared packages (`content-cms.contracts.ts`, matrice RBAC), Back-office Plateforme/Admin (écran d'édition et d'approbation), Web Publique Client (lecture du contenu publié, bilingue FR/EN, repli statique). **Broker Back-office : aucun changement. runtime/Docker : aucun.** Les parcours public (anonyme, lecture seule) et admin (authentifié, MFA) restent séparés.

## Why
Le contenu éditorial public (FAQ, guides, glossaire, pages légales) est codé en dur dans `apps/public/app/content/**`. Toute correction demande un déploiement, et les pages légales d'un pays (par exemple le Sénégal) n'ont aucune surcharge propre : elles affichent « À compléter ». Le rôle `content_admin` existe (permission `content:*`) sans écran ni API.

## User stories
1. **(P1) Content Admin.** Il rédige un brouillon (FAQ, guide, terme de glossaire, surcharge légale d'un pays, en FR ou EN), le soumet à validation, et peut le retirer ou le corriger avant publication.
2. **(P1) Validateur (second rôle).** Un autre acteur (compliance_admin, super_admin ou un autre content_admin) relit, approuve (publication) ou rejette avec un motif. Une surcharge légale n'est approuvable que par compliance_admin ou super_admin.
3. **(P1) Visiteur.** Il ne voit que du contenu publié ; s'il n'y a rien de publié (ou si l'API est indisponible), le site affiche exactement le contenu statique actuel.
4. **(P2) Révision.** Pour modifier un contenu publié, on crée un nouveau brouillon (version suivante) ; la version publiée reste en ligne jusqu'à l'approbation de la nouvelle, qui archive l'ancienne dans la même opération.

## Requirements
- **FR-001 (modèle).** Une table unique et versionnée `ContentEntry` : `kind` (`faq`, `guide`, `glossary`, `legal_override`), `entryKey`, `locale` (`fr`/`en`), `countryCode` (uniquement `legal_override`, ISO majuscules), `version`, `status` (`draft`, `pending_review`, `published`, `archived`), `payload` JSON validé par type, traçabilité (créateur, soumetteur, décideur, dates, note de décision). Au plus une version `published` par (`kind`, `entryKey`, `locale`, `countryCode`) ; au plus une version ouverte (`draft` ou `pending_review`) par même clé.
- **FR-002 (cycle).** `draft → pending_review` (soumission, validation du contenu) ; `pending_review → published` (approbation) ; `pending_review → draft` (rejet avec motif obligatoire, ou retrait par l'auteur) ; `published → archived` (retrait avec motif obligatoire) ; `draft → archived`. Toute autre transition est refusée (409). Un contenu publié n'est jamais modifié en place.
- **FR-003 (approbation, quatre yeux).** L'approbation exige la permission `content:approve` ET que l'approbateur soit un acteur différent de celui qui a soumis l'entrée (aucune auto-approbation, `super_admin` compris). Une `legal_override` n'est approuvable que par `compliance_admin` ou `super_admin`. Chaque refus est audité.
- **FR-004 (permissions).** Lecture admin : `content:read` (content_admin, compliance_admin, super_admin). Création, modification, soumission, retrait : `content:create`/`content:update`/`content:submit` (content_admin, super_admin). Approbation, rejet, archivage : `content:approve` (content_admin, compliance_admin, super_admin). Tout autre rôle, y compris `admin_pays`, `support_admin`, les rôles courtier et l'anonyme : refus audité. Authentification et MFA exigées.
- **FR-005 (texte brut, anti-XSS).** Aucun HTML ni balisage : les schémas refusent `<` et `>` et les caractères de contrôle. Le site public rend chaque valeur comme texte React (jamais `dangerouslySetInnerHTML`, jamais de lien généré depuis le contenu). Les longueurs sont bornées.
- **FR-006 (conformité éditoriale).** À la soumission et à l'approbation, le texte est contrôlé par les listes de formulations interdites (constitution VIII : `findForbiddenWordingAnyLanguage`, et le vocabulaire éditorial de la charte `findForbiddenEditorialWordingForLocale`). Un texte en infraction est refusé (422 `FORBIDDEN_WORDING`) et l'échec est audité. Aucune IA n'intervient dans la rédaction, la relecture ni la publication.
- **FR-007 (audit).** Création, modification, soumission, retrait, approbation, rejet, archivage, révision et chaque refus (accès, auto-approbation, formulation interdite) produisent une entrée d'audit (`content_cms.*`) avec identifiant, type, clé, langue, pays, version, statuts avant/après, sans recopier le texte.
- **FR-008 (lecture publique).** `GET /public-content?locale=fr|en&country=XX` (sans authentification, `Cache-Control: public, max-age=60`) renvoie uniquement le contenu publié de la langue demandée ; `legal` n'est rempli que pour le pays demandé. Jamais de brouillon, de contenu en attente, d'identifiant de personne ni de note interne.
- **FR-009 (fusion et repli statique).** Le site public fusionne le contenu publié avec le statique : un guide remplace le statique de même `slug`, un terme de même libellé (insensible à la casse) remplace l'entrée statique, une question identique (texte normalisé) remplace la réponse statique, les autres entrées publiées s'ajoutent ; une surcharge légale remplace les sections de même `id` de la page légale du pays (même sémantique que `getLegalPage`) et ses placeholders remplacent ceux de la surcharge statique. Si rien n'est publié, si l'API répond une erreur ou dépasse le délai (2 s), le rendu est strictement celui d'aujourd'hui.
- **FR-010 (bilingue).** Chaque entrée appartient à une langue ; FR et EN ont chacune leur cycle. Une langue sans contenu publié retombe sur le statique de cette langue (jamais sur l'autre langue).
- **FR-011 (écran admin).** Section « Contenu » du back-office Plateforme : liste filtrable (type, langue, statut, pays), création/édition d'un brouillon par formulaire texte (pas d'éditeur riche), boutons Soumettre / Retirer / Approuver / Rejeter / Archiver / Réviser affichés selon les capacités de l'acteur, motif obligatoire pour rejeter et archiver, historique des versions d'une clé. Aucun export ni exécution de contenu saisi.
- **FR-012 (tests).** Unitaires (schémas, cycle, quatre yeux, fusion), intégration HTTP (gardes d'accès par rôle, MFA, public sans brouillon, fusion, audit), et spécifications Playwright « sources » côté admin et public.

## Hors périmètre (documenté)
- Éditeur riche / Markdown / images / pièces jointes ; planification de publication ; prévisualisation de la page publique avant publication.
- Traduction automatique et suggestions IA (interdites par le lot).
- Masquer une entrée statique sans la remplacer ; suppression physique d'une version.
- Pages institutionnelles autres que FAQ/guides/glossaire/légal, textes de consentement (déjà gérés par la spec 050).
- Ré-hébergement du contenu statique dans la base (aucun import automatique : le statique reste le repli).
