# Feature Specification: Quote Notification Delivery

**Feature Branch**: `044-quote-notification-delivery`
**Created**: 2026-09-19
**Status**: Implemented and validated 2026-09-19
**Validation State**: Validated. D1 and D2 shipped as decided. This spec opens no feature flag and adds no HTTP route.
**Continuous Workflow Eligible**: Yes.

## Why this spec exists

No quote email has ever left the platform, in any environment.

`QuoteNotificationService.queueVisitor` and `queueBroker` write a `Notification` row with
`emailStatus: "queued"` and enqueue a job on `visitor-quote-notifications` /
`broker-lead-notifications`. **Nothing consumes those queues.** There is no worker, no consumer, no
scheduled drain - the only reference to the queue names in the whole repository is the constant that
declares them.

Found on 2026-09-19 while running the visitor journey end to end after spec 043 made it reachable:
the submission succeeds, the routing decision is taken, the lead lands in the broker's CRM, two
`Notification` rows are created - and Mailpit stays empty. The rows sit at `queued` forever.

The consequence is not cosmetic. A broker who does not open the portal never learns a lead arrived,
and a visitor gets no written trace of a request they consented to transmit. The PRD coverage map
claimed "auth/quote notifications" as implemented; only the auth half was.

Everything needed already exists and is proven by the auth flow: `RuntimeEmailDeliveryService`
(Mailpit and SMTP transports, preview mode, error classification, masked audit),
`NotificationsService.updateDelivery`, and the partner-webhook worker as the established pattern for
deferred delivery in this codebase. This spec is wiring, not new infrastructure.

## Constitutional Scope & Compliance (Principle V)

- **Technical platform role**: Unchanged. An email states that a request was transmitted or received. It never quotes, prices, advises, confirms cover or commits anyone.
- **Impacted application(s)**: Backend API (notifications module), runtime (a delivery worker script, like `partner-webhooks:deliver-due`). No change to any front-end.
- **Affected scopes**: Countries and products only as content of the message; the recipient is either the visitor of a quote request or the partner tenant of a lead assignment.
- **Frontend separation**: Unchanged. Emails link to the public tracking page for a visitor and to the broker back-office for a partner; never the other way round.
- **Required feature flags**: None new. Delivery follows the existing email runtime configuration (`EMAIL_SERVICE_TYPE`, `EMAIL_PREVIEW_MODE`), exactly like auth emails. With email disabled, notifications are marked `not delivered` and audited rather than silently dropped.
- **Consent and transmission**: The visitor consented to transmission, which is what the confirmation reports. No email is sent for a request that was refused for missing consent - there is no notification row for it in the first place, and the worker never creates one.
- **Partner license controls**: Not touched. The lead already passed eligibility before the notification existed.
- **Audit and data history**: Every attempt is audited through the existing `email.delivery.*` actions with a masked recipient, plus a notification-level transition. A failed delivery is recorded on the notification. **Correction made during implementation**: this line originally claimed that a permanently failed partner notification would publish `notification.failed` to the partner webhook (spec 039). It does not. `updateDelivery` fires that event only when **both** channels are `failed`, and WhatsApp ships disabled, so its status never leaves `queued` - the condition can never be met for a quote notification. Changing it would alter spec 039's semantics for every notification type, which is a decision of its own and is not taken here. The failure is still recorded and audited; the partner simply is not told through its webhook. Left as a known limitation rather than quietly widened.
- **Security and RBAC**: The worker runs as an operator process, not over HTTP. There is no new route and no way to trigger a send from a browser.
- **Routing impact**: None. Delivery happens after routing and cannot change an assignment.
- **AI impact**: None. No message content is generated by a model.
- **UX/content restrictions**: Rendered bodies pass the same forbidden-wording guardrail as every public surface: never "Acheter", "Souscrire maintenant", "Contrat valide", "Garantie acceptee", "La meilleure assurance", and no price, no promise of cover, no ranking claim.
- **Data minimisation**: See D1. This is the decision that shapes the feature.
- **Workflow continuity**: Not interrupted.

## Decisions

### D1 - Emails carry a pointer, never the lead

The broker email states that a lead arrived, with its public reference, country and product, and
links to the broker back-office. It contains **no visitor contact details and no answers**.

Email leaves the platform's access control: it is forwarded, archived on third-party servers, read on
shared devices, and it outlives any consent withdrawal. Every control the platform applies to this
data - tenant checks, PII masking, audited detail reads, the retention clock - stops at the mail
gateway. Putting the lead in the body would move the personal data of a visitor who consented to
*transmission to an eligible broker* into an uncontrolled channel, and would make a lead readable by
anyone who later gains access to a mailbox.

The visitor email carries their own public reference and tracking link, no broker identity (the
platform does not disclose who was selected before contact), and no price.

The cost is one extra click for the broker. That is the correct trade.

### D2 - A worker, run by the operator, not an in-process consumer

Delivery runs as `npm run quote-notifications:deliver-due`, mirroring
`partner-webhooks:deliver-due`: a bounded batch, an explicit limit, exit code and a JSON summary on
stdout. It is scheduled by the operator, like every other deferred job in this codebase.

An in-process BullMQ consumer inside the API was rejected: it would make email delivery a side effect
of the request-handling process, so a slow or failing SMTP would consume API capacity, and a restart
mid-send would leave notifications in an unknown state. The worker is restartable and idempotent by
construction because the notification row is the state.

**Idempotence** is the load-bearing property: the worker only picks rows whose `emailStatus` is
`queued` or `retryable`, and moves each to `sent` or `retryable`/`failed` before returning. Running
it twice never sends twice.

**Failure policy**: a transport failure moves the row to `retryable` and increments its retry count;
past a cap (default 3) it becomes `failed` and is audited. A
configuration failure (email disabled) is not a retry: the row stays `queued` and the run reports it,
because retrying a disabled mailer forever would bury a real operational problem under noise.

## Requirements

- **Templates**: a `QuoteEmailTemplateService` rendering `visitor_quote_confirmation`, `visitor_quote_non_routable` and `broker_lead_assigned`, in French, text and HTML, with the platform disclaimer already used everywhere ("plateforme technique de comparaison indicative et de mise en relation"). Extend `EmailPurpose` with the three quote purposes so the existing audit path labels them correctly.
- **Recipient resolution**: `visitor:<publicReference>` resolves through the quote request to its prospect's email; `partner:<tenantId>` resolves to the partner tenant's primary email. A notification whose recipient cannot be resolved is marked `failed` with an audited reason rather than skipped silently.
- **Delivery service**: `QuoteNotificationDeliveryService.processDueNotifications({ limit })` reading queued/retryable quote notifications, rendering, sending through `RuntimeEmailDeliveryService`, and calling `NotificationsService.updateDelivery`. WhatsApp status is left untouched - this spec does not open that channel.
- **Guardrail**: every rendered body is checked with `findForbiddenWording` before sending; a hit refuses the send, marks the notification `failed` and audits the matched wording. A regulated word in an outbound email is a compliance incident, not a formatting bug.
- **Worker**: `scripts/quote-notification-delivery-worker.ts` + npm script, with a bounded `ASSURMATCH_QUOTE_NOTIFICATION_DELIVERY_LIMIT` (1-100, default 25).
- **Runbook**: `docs/runbooks/` gains the operational procedure, including what to check when notifications accumulate at `queued`.

## User Scenarios & Testing

1. **Given** a routed quote request with a visitor and a broker notification at `queued`, **When** the worker runs, **Then** both are delivered, both rows move to `sent`, and Mailpit holds two messages.
2. **Given** the same state, **When** the worker runs **twice**, **Then** exactly two messages exist - the second run reports zero due.
3. **Given** a broker notification, **When** it is delivered, **Then** the body contains the public reference, country and product and a link to the back-office, and contains **neither the visitor's email nor phone nor any answer value**.
4. **Given** a visitor notification, **When** it is delivered, **Then** the body contains the visitor's own reference and no broker name, no price and no forbidden wording.
5. **Given** an SMTP transport that throws, **When** the worker runs, **Then** the notification becomes `retryable` with an incremented count; **and** after the cap it becomes `failed` and is audited. (The partner webhook is not notified - see the corrected audit note above.)
6. **Given** `EMAIL_SERVICE_TYPE=disabled`, **When** the worker runs, **Then** nothing is sent, rows stay `queued`, and the run reports them as not configured - a disabled mailer never consumes the queue.
7. **Given** a template that would render a forbidden word, **When** delivery is attempted, **Then** the send is refused, the row is `failed`, and the matched wording is audited.
8. **Given** a notification whose partner has no primary email, **When** the worker runs, **Then** it is `failed` with `recipient_unresolved`, never skipped.

## Validation

- `npm run validate`; unit tests for templates and guardrail; integration tests for the delivery service covering idempotence, retry, disabled mailer and recipient resolution; runtime Postgres smoke extended to assert a delivered notification; then the local journey with a real submission and two messages visible in Mailpit.

## Found while implementing

- **The retry cap never bit.** `NotificationsService.updateDelivery` wrote the statuses but not the
  retry count, so a row moved to `retryable` came back with `retryCount: 0` and would have retried a
  permanently failing recipient forever. Caught by the cap test, fixed by persisting the count with
  the status.
- **`QuoteRequestRecord` lies about its own shape.** It declares `countryCode` and `productKey`, but
  the table stores only the ids and the Prisma repository strips the codes on write - so every record
  read back from PostgreSQL has them `undefined`. The first real worker run crashed on it. The
  runtime now resolves the codes from the catalogue, and the delivery service refuses with
  `quote_scope_unresolved` rather than rendering an email full of blanks. Unit tests could not have
  caught this: the in-memory record carries the fields the type promises.

## Explicit non-goals

- No WhatsApp or SMS delivery: those stay behind their own disabled flags (spec 038).
- No lead content in any email (D1).
- No in-process queue consumer (D2).
- No new HTTP route, and no way to trigger a send from a browser.
- No retry scheduler: the operator's cadence drives the worker, as with partner webhooks.
