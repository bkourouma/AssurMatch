# Feature Specification: IA admin, flags IA par pays/produit et intégrations partenaires (spec 074)

**Status**: Validated (lot 7 « IA admin et intégrations partenaires » mandaté par le superviseur le 2026-10-21 ; spec standard, aucun `[NEEDS CLARIFICATION]`)
**Input**: PRD v0.3 §10.3 (IA admin), EPIC H (H-07 clés d'API, webhooks et liste d'autorisation ; H-08 envoi de test), constitution v1.4.0 (III flags globaux, pays et produit ; V IA désactivable par pays et produit ; XI aucune activation accidentelle), specs 033/039 (Partner API et webhooks), 034/050/059/064 (IA, flags, voie de politique de conformité).
**Impacted surfaces**: Backend API (modules `ai`, `partner-integrations`, `feature-flags`, câblage HTTP, runtime), shared packages (contrats), Back-office Plateforme/Admin (écrans `/ai-assistance`, `/ai-assistance/flags`, `/partner-integrations`, `/messaging`). **Broker Back-office : aucun changement** (les clés d'API partenaire sont créées par l'administrateur, jamais par le courtier ; les deux apps restent séparées). Web Publique Client : aucun changement. Base de données : aucune migration (les flags pays/produit vivent déjà dans `Country.flags` / `Product.flags` et `FeatureFlag`).

## Why
1. L'écran « Assistance IA » de l'admin sert les insights, mais les flags IA par pays (`country_ai_enabled`) et par produit (`product_ai_scoring_enabled`, `product_ai_form_assistant_enabled`) ne peuvent être modifiés par aucune voie : le catalogue les refuse (liste blanche, spec 050 R3), la route PATCH des flags les refuse (flags à portée, spec 050) et le script d'exploitation ne traite que les flags globaux. L'IA ne peut donc jamais être ouverte pour un pays ou un produit sans accès base.
2. H-07 : la page des intégrations partenaires est en lecture seule alors que les routes d'écriture existent (création et révocation de clés, endpoints webhook, liste d'autorisation).
3. H-08 : aucun moyen de vérifier qu'un endpoint webhook (ou un canal de messagerie) fonctionne sans attendre un vrai événement.

## User stories
1. **(P1) Compliance/Super admin.** Depuis `/ai-assistance/flags`, il voit l'état des trois flags IA par pays et par produit, et les DÉSACTIVE par une voie dédiée : MFA, rôles `super_admin`, `compliance_admin` ou `ai_admin`, motif obligatoire, audit `feature_flag.policy_applied`. L'ACTIVATION ne passe pas par HTTP : elle est refusée (403 `ACTIVATION_VIA_OPS_ONLY`, auditée) et se fait par `npm run ops:apply-flag-policy -- --scope-type ... --scope-id ...` (référence de politique + approbateur + motif). **Note : dérogation d'activation par HTTP NON retenue en attendant la décision du propriétaire ; spec 035 l.15 et spec 050 scénario 6 restent applicables.**
2. **(P1) Admin plateforme.** Depuis `/partner-integrations`, il crée une clé d'API (secret affiché une seule fois), la révoque avec un motif, crée et active/suspend un endpoint webhook (secret de signature affiché une seule fois), ajoute et révoque une origine de la liste d'autorisation.
3. **(P2) Admin plateforme.** Il envoie un événement de test signé à un endpoint webhook et voit la classe de réponse (2xx, 4xx, 5xx, erreur réseau, bloqué par la politique). Un super admin envoie un message de test sur un canal SMS/WhatsApp configuré depuis `/messaging`.

## Requirements
### IA : flags par pays et produit
- **FR-001 (voie dédiée).** Nouveau service `AiScopeFlagPolicyService` et routes `GET /admin/ai/scope-flags` (état) et `POST /admin/ai/scope-flags` (changement). Seules les clés `country_ai_enabled` (pays), `product_ai_scoring_enabled` et `product_ai_form_assistant_enabled` (produit) sont acceptées. Aucune autre clé, aucun autre type de portée.
- **FR-002 (protection).** MFA obligatoire. Over HTTP, toute demande `value: true` est refusée (403 `ACTIVATION_VIA_OPS_ONLY`, auditée `feature_flag.change_refused`) quel que soit le rôle. Désactivation : `super_admin`, `compliance_admin` ou `ai_admin`, `reason` (8-500) obligatoire, ni référence ni approbateur ; la portée `countryScopes`/`productScopes` de l'acteur est respectée pour tous les rôles (hors portée : 403). L'activation par l'opération (`AiScopeFlagPolicyService.activateViaOps`, jamais routée) exige `super_admin` ou `compliance_admin`, `reference` (3-120), `approvedBy` (3-120) et `reason`. Une valeur déjà égale est un no-op sans écriture.
- **FR-003 (garde-fous métier).** Activer `product_ai_scoring_enabled` ou `product_ai_form_assistant_enabled` est refusé pour un produit de sensibilité `highly_sensitive` (raison `SENSITIVE_PRODUCT_AI_REQUIRES_EXCEPTION`, y compris par la commande d'exploitation). Aucune activation ne dépend du flag global : le flag global IA reste fermé par défaut et passe par `ops:apply-flag-policy` (inchangé, lecture seule sur l'écran).
- **FR-004 (audit et historique).** Succès : écriture dans `Country.flags`/`Product.flags` (source lue par le parcours public et la passerelle IA), ligne `FeatureFlag` + historique via `FeatureFlagsService.applyCompliancePolicy` (si cet appel échoue, l'écriture `Country.flags`/`Product.flags` est annulée : jamais d'état changé sans trace) (action `feature_flag.policy_applied`, contexte clé, valeur avant/après, portée, référence, approbateur), invalidation du cache public. Chaque refus est audité (`feature_flag.change_refused`, raison, valeur demandée).
- **FR-005 (aucune brèche HTTP).** Les routes existantes `PATCH /admin/feature-flags/:id` et `POST .../flags` du catalogue continuent de refuser ces clés. Les trois clés rejoignent la liste des flags sensibles de la politique de mutation (`sensitive-feature-flag-policy.ts`) pour qu'aucun appel `setFlag` ne les modifie.
- **FR-006 (écran).** `/ai-assistance/flags` (lien depuis `/ai-assistance` et la navigation) : tableau des pays (1 flag) et des produits (2 flags), état, bouton « Désactiver » (motif) pour un flag actif ; pour un flag inactif, aucun bouton « Activer » mais la procédure `npm run ops:apply-flag-policy` (avec `--scope-type`/`--scope-id`) en lecture seule ; messages d'erreur en français ; flags globaux IA en lecture seule avec la commande d'exploitation ; historique récent des changements.

### Partenaires : clés d'API, webhooks, liste d'autorisation (H-07)
- **FR-007 (clés d'API).** Création : partenaire (liste des courtiers), nom, scopes, motif. La réponse contient `rawKey` : l'écran l'affiche une seule fois dans la réponse de l'action (jamais stockée, jamais dans l'URL, jamais dans les journaux serveur, jamais dans l'audit). Révocation avec motif.
- **FR-008 (webhooks).** Création d'un endpoint (partenaire, URL, événements ; `signingSecret` affiché une seule fois), activation/suspension (PATCH), ajout/révocation d'une origine d'autorisation (origine, chemin facultatif, motif).
- **FR-009 (envoi de test, H-08).** `POST /admin/partner-integrations/webhook-endpoints/:id/test` (`{ reason }`) : MFA + `partners:update`. Envoie un événement `webhook.test` (charge utile sans donnée personnelle) à l'endpoint avec les mêmes en-têtes signés que les livraisons réelles (`X-AssurMatch-Signature` HMAC-SHA256 du secret de l'endpoint, horodatage, id d'événement, clé d'idempotence), mêmes contrôles d'URL (politique anti-SSRF, liste d'autorisation, DNS, redirections bloquées, délai 10 s). Fermé par défaut : refusé avec `feature_disabled` si `partner_webhooks_enabled` est fermé ou si l'envoi sortant n'est pas activé sur le service (pas de trafic sortant sans flag). Limite : 1 test par endpoint et par 30 s. Aucune ligne de livraison n'est créée ; audit `partner_webhook.test_sent` (classe de réponse, durée, sans corps ni secret). Réponse : `{ endpointId, eventId, eventType, outcome, responseClass, durationMs, sentAt }`.
- **FR-010 (messagerie, H-08 du PRD).** Bouton « Envoyer un message de test » sur `/messaging` (canal, destinataire, motif) pour `super_admin`, qui appelle la route existante `POST /admin/messaging/test` (aucun changement backend) ; le résultat est un message (envoyé/refusé) sans secret.
- **FR-011 (secrets).** Aucun `rawKey`, `signingSecret`, secret fournisseur ni `keyHash` dans les journaux, l'audit, les URL, les cookies ou le stockage du navigateur ; les composants client affichent le secret depuis l'état de l'action uniquement, avec un avertissement « affiché une seule fois ».

## Hors périmètre (documenté)
- Flags globaux IA : restent sur `ops:apply-flag-policy` (zone voisine du lot 5, intacte).
- Flags IA par partenaire et par plan : inchangés.
- Gestion des clés d'API par le courtier lui-même (Broker Back-office) : non demandée, le courtier gère déjà ses endpoints via la Partner API.
- Mise à jour d'une origine d'autorisation (seulement création et révocation).

## Hypothèses métier (prudentes, réversibles)
- Activer l'IA par pays ou produit est une décision de conformité : `super_admin`/`compliance_admin` seulement, avec référence et approbateur. Désactiver est ouvert à `ai_admin`.
- Les produits `highly_sensitive` n'ouvrent pas l'IA sans exception documentée (refus).
- L'envoi de test webhook est refusé tant que `partner_webhooks_enabled` est fermé.
